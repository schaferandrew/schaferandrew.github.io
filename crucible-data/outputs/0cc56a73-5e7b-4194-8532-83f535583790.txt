### Design Decisions & Rationale

1. **Visibility rules for drafts** — `GET /api/articles` and `GET /api/articles/feed` only return `published` articles. `GET /api/articles/:slug` returns 404 for non-published articles unless the caller is the author or an editor (for `in_review`). This prevents the public from discovering unapproved work while letting workflow participants access what they need.

2. **Editors cannot see arbitrary drafts** — Editors may only see `in_review` articles (for the review queue). Once an article is rejected it goes back to `draft`, and only its author can see it until resubmitted. This respects the principle that editors review only what's been *submitted* for review.

3. **Self-approval prevention** — `approve` and `reject` both check that the editor is not the article author, returning 422. Non-editors get 403 when trying to approve/reject.

4. **Review comment privacy** — `reviewComment` is only exposed in the JSON when the viewer is the article's author or an editor. For everyone else it's `null`. Published articles always have `null` (comments are cleared on submit/approve).

5. **Backward compatibility** — Existing articles created without a `status` field default to `published`, preserving current behavior. The new fields are appended to the `Article` JSON shape without changing existing fields. The contract test verifies all original fields remain present.

6. **`reviewComment` is a single string, not a conversation** — The brief says "Feedback is a conversation" but the API spec says `reviewComment: string | null`. I implemented what the API contract defines: a single comment string set on rejection, cleared on resubmit. A conversation thread would need a separate resource.

### What I'd Flag in Code Review

- **Comments on non-published articles** — `GET /api/articles/:slug/comments` currently lists comments on any article, but non-published articles are 404'd by `getArticle` before they reach the comments route. Comments are "derived from" the article, so this is correct — but adding an explicit guard at the comment service level would be more defense-in-depth.

- **Tag listing could leak article existence** — `GET /api/tags` counts tags across all articles, including drafts. If a tag only exists on a draft article, the tag still shows up in the tag listing, leaking the tag name. For stricter privacy, `popularTags` should only count published articles. This wasn't in the explicit requirements but is worth calling out.

- **Feed pagination for editors** — The review queue pagination uses offset/limit which, with `oldest first` ordering, works correctly. But if new articles enter the review queue while someone is paging through it, items could shift. This is an accepted tradeoff for the current design.

- **No rate limiting or spam protection** — New endpoints with write operations (submit/approve/reject) have no rate limiting. For production, these should be behind appropriate throttling.

- **Editor config at app start** — Editors are loaded once at startup from the `EDITORS` env var. There's no runtime mechanism to add/remove editors without restarting. For a real system, you'd want this in the database with admin API endpoints.
