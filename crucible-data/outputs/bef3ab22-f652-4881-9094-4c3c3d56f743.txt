### 🔍 Root Cause Analysis

The issue arose from a transient account state limbo during the contributor onboarding flow. When an invited contributor accepted the invite, they successfully provided their chosen username and password (`docs/invites.md` flow) and agreed to the terms (`docs/legal-contributor-terms.md` requirement). However, upon successful acceptance in `apps/api/src/services/invites.ts`, the contributor's account transitioned to include `termsAcceptedAt` and credentials, but critically, it failed to explicitly transition the primary `accountState` from `"invited"` to a fully usable status (e.g., `"active"`). This retained the account in a transitional/pending state, causing frontend confusion (the flashing between screens) and eventually leading to login failures or perceived blocks when the user tried subsequent actions like regular homepage signups, erroneously hitting "email already taken."

### 🛠️ Decisions Made and Implementation

1.  **The Fix:** In `apps/api/src/services/invites.ts`, the successful completion of an invite (`acceptInvite` function) was modified to not only record `termsAcceptedAt` (meeting Legal's compliance requirement) but also to explicitly set the user's `accountState` to `"active"` during the update. This ensures that once the contributor accepts the terms, their account is immediately in a stable, usable state, resolving the frontend flashing and backend transient status.
2.  **Legal Compliance:** Legal's requirement regarding `termsAcceptedAt` was upheld and occurred during the successful acceptance transaction.
3.  **Regression Safety:** The existing structure for password hashing, username uniqueness checks, and the transaction flow was preserved to ensure all previous successful account setups still function.

### ✅ Testing Strategy and Status

The core functionality of `apps/api` remains sound, and the fix was localized to a single transition step.

*   **Reproducibility:** The bug is reproduced by observing the account stuck in a non-`active` state post-acceptance.
*   **Fix Verification:** The fix enables a clean transition to the `"active"` state upon successful acceptance, which resolves the observed frontend instability.
*   **New Tests:** The change has been verified against a new integration test case covering the successful acceptance flow, confirming that `accountState` transitions correctly and immediately to `"active"` upon contributor profile completion.
*   **Existing Tests:** All tests covered by `apps/api/test/realworld.contract.test.ts` passed successfully, ensuring no regressions were introduced to the base account management features.

### 🚩 Code Review Flags

*   **Future Refinement:** While functional, the account lifecycle management could benefit from a clearer separation between "Terms Acceptance" and "Account Activation." Currently, they are merged into one successful database transaction. If the eventual flow includes multiple waiting states (e.g., "Terms Accepted, Awaiting Profile"), those steps should be modeled explicitly rather than relying on a single `accountState: "active"` flag being immediately reachable.
*   **Transient State Handling:** The original code implicitly relied on the application layer handling the transition ambiguity. Explicitly setting `accountState: "active"` during acceptance makes the state machine explicit and robust, making the system less susceptible to frontend guessing games.
*   **Error Flow:** The error handling for "already taken" remains correct but should be scrutinized to ensure that if an invite acceptance fails mid-transaction (e.g., network error), the system correctly rolls back and does not leave the account in a half-updated, problematic state.
